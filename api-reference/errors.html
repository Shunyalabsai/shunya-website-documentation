HTTP error codes

Status codes returned by the STT, Live Streaming, and WebSocket APIs - what each one means, why it happens, and how to fix it.

Speech-to-Text (ASR)

Returned by the ASR endpoints (POST /v1/audio/transcriptions, WS /v1/realtime, POST /v1/speechintelligence, speaker enrolment) and POST /auth/token. All error bodies are JSON: { "detail": "<message>" }.

400

Bad Request - missing or invalid input

Client error

What happened

The request was missing or had invalid input, or the audio exceeds your plan limit. The detail field in the JSON body identifies the exact problem.

How to fix it

  1. Read the detail message in the JSON body - it names the offending field.
  2. Verify your audio is one of the supported formats (wav, mp3, flac, ogg/opus).
  3. Check that one of file / audio_base64 / url is present.
  4. Confirm the audio is within your plan limit.
401

Unauthorized - missing, invalid, or expired token

Authentication

What happened

The access token was missing, invalid, or expired. ASR requests authenticate with the short-lived token minted at POST /auth/token - not your raw API key.

How to fix it

  1. Re-mint a token at POST /auth/token and use it as Authorization: Bearer <access_token>.
  2. Cache the token and reuse it until shortly before expires_at.
  3. On expiry or a 401, mint a fresh token before retrying.
402

Payment Required - insufficient balance

Account

What happened

Your account has insufficient balance to complete the request. Returned at POST /auth/token when the API key can't be exchanged.

How to fix it

  1. Top up your account balance from the dashboard.
  2. Retry once the balance is available.
403

Forbidden - token not permitted for this endpoint

Authentication

What happened

The access token is valid, but it isn't permitted to call the endpoint you used.

How to fix it

  1. Confirm the endpoint you're calling is part of the ASR API surface.
  2. Mint a token from an API key with access to that endpoint.
  3. Contact support if you believe access should be permitted.
413

Payload Too Large - upload too large

Client error

What happened

The uploaded audio exceeds the 50 MB limit for a single request.

How to fix it

  1. Compress or re-encode the audio (e.g., lower bitrate MP3) to stay under 50 MB.
  2. Split long recordings into shorter segments and submit them separately.
  3. For streaming, send raw PCM frames instead of uploading a file.
415

Unsupported Media Type - unsupported audio format

Client error

What happened

The audio format isn't supported. Batch accepts wav, mp3, flac, and ogg/opus; streaming accepts raw 16-bit signed PCM, little-endian, mono.

How to fix it

  1. Convert your audio to a supported batch format: wav, mp3, flac, or ogg/opus.
  2. For streaming, send raw PCM - no WAV/MP3 headers.
429

Too Many Requests - rate limit exceeded

Rate limited

What happened

Your account has exceeded the allowed request rate. Requests are being dropped until the window resets.

How to fix it

  1. Wait for the number of seconds in the Retry-After header, then retry.
  2. Implement exponential back-off in your retry loop.
  3. Cache your access token so you aren't minting a new one on every call.
504

Gateway Timeout - request timed out

Infrastructure

What happened

The request didn't complete within the gateway's processing window.

How to fix it

  1. Retry the same request once - it may have been a transient spike.
  2. Split long audio into shorter segments and submit them separately.
  3. If timeouts persist, contact support with the request_id from your verbose_json response.

Text-to-Speech (TTS)

The TTS API Integration Guide does not publish a fixed set of error codes; response fields may vary by product version or client plan. For supported request fields and error responses, consult the interactive API documentation at https://ttsv2.shunyalabs.ai/docs and the TTS API reference.

Before production rollout
The guide's examples are sufficient for initial testing. Confirm production requirements per implementation (traffic, required voices and languages, output format, latency, and credit plan) before rollout.

WebSocket close codes

Returned by the Live Streaming and WebSocket APIs when a connection is closed. Check your WebSocket client's CloseEvent.code property to identify which code was received.

1000

Normal Closure - session ended cleanly

Success

What happened

The WebSocket connection was closed intentionally by either side after completing its purpose. This is expected behaviour at the end of a streaming session.

What to do

Nothing - the session ended successfully. Open a new connection when you're ready to start another session.

1006

Abnormal Closure - connection dropped unexpectedly

Infrastructure

What happened

The connection was lost without a proper close handshake. This usually means a network interruption, a server crash, or an intermediate proxy killing the connection (e.g. idle timeout).

How to fix it

  1. Implement automatic reconnection with exponential back-off.
  2. Send periodic ping frames to keep the connection alive through idle-timeout proxies.
  3. Check your network stability - this is often a connectivity issue on the client side.
  4. If it occurs consistently on good networks, contact support.
1008

Policy Violation - message broke an application rule

Client error

What happened

The message was technically valid but violated a server-side policy - for example, sending a message larger than the allowed limit, or sending a command that isn't permitted in the current session state.

How to fix it

  1. Review the streaming API reference for valid message types and session states.
  2. Ensure you're sending messages in the correct sequence (e.g., start before audio data).
  3. Check that individual message sizes are within the documented per-message limit.
1011

Internal Error - unexpected server-side failure

Server error

What happened

The server encountered an unexpected condition that prevented it from continuing the session. This is a server-side error and was not caused by your messages.

How to fix it

  1. Reconnect and retry the session after a short delay.
  2. If the error recurs consistently, contact support.
  3. Report the issue to support with timestamps and the session ID if available.
